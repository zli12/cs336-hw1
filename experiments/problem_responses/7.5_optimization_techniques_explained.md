# 7.5 Optimization Techniques Explained — A Student's Guide

This is a companion to the [`7.5 Leaderboard Speedrun Report`](./7.5_leaderboard_report.md).
That report is the "what we did and how it scored" writeup. This one is the
"what each technique actually *is* and *why* it works" writeup, aimed at
someone who is meeting these ideas for the first time.

For every modification we tried in 7.5, the goal here is to answer four questions:

1. **What is it?** — a plain-English description.
2. **How does it work?** — the mechanism, with the minimum math needed.
3. **Why does it work?** — the intuition for what problem it solves.
4. **When does it fail?** — the real failure modes (some of which we hit).

Wherever helpful we ground the explanation in the actual numbers we measured
on the OpenWebText leaderboard run (`d_model=1024`, `L=8`, `vocab=32k`, A100-40GB).

---

## How to think about the four categories

The 7.5 modifications fall into four very different groups. It's worth
internalizing this taxonomy *before* diving into individual techniques,
because the right way to use each technique depends on which group it's in.

| Group | What it changes | Quality impact | When to use it |
|---|---|---|---|
| **Infrastructure** | Throughput only — same math, faster GPU code | ≈ 0 nats (within noise) | Always, by default |
| **Quality wins** | Architecture / loss / init — well-validated published mods | Small per-mod, additive | Always, by default |
| **Speedrun mods** | Same areas — recent, less proven | Variable; some help, some hurt | Ablate first; keep winners |
| **Methodology** | How you *find* the right config, not what's in it | Indirect | Always |

A common mistake is to treat all four as the same kind of change. They
aren't. Infrastructure is "free if it works"; speedrun mods are "lottery
ticket — buy one, but only commit if it pays off."

## Group 1 — Infrastructure speedups (free throughput, no quality change)

The defining property of this group: the loss curve should look numerically
identical (within optimizer noise of about ±0.005 nats), but training is
much faster. You're changing how the GPU does the math, not what math gets
done. **In our run this group alone gave us a 7.32× throughput uplift over
the 7.4 A10G fp32 setup**, which is what made the entire rest of the
leaderboard plan affordable.

### 1.1 bf16 mixed precision

**What.** Run the forward pass and loss in 16-bit "brain float" (bf16)
arithmetic instead of 32-bit float, while keeping the parameters and
optimizer states in fp32.

**How.** Wrap the forward + loss in
`torch.autocast(device_type="cuda", dtype=torch.bfloat16)`. PyTorch
auto-casts matmuls and a few other ops to bf16; everything else stays
fp32. The optimizer step uses fp32 master weights so the parameter updates
are still numerically clean.

**Why.** Modern GPUs (A100, H100) have dedicated bf16 tensor cores that
do matmul ~2× faster than fp32 and use ~half the memory bandwidth.
Crucially, bf16 has the *same* exponent range as fp32 (8 bits), so unlike
fp16 it doesn't overflow on large activations. You only lose precision in
the mantissa (7 bits vs 23) — and since SGD/Adam already adds gradient
noise much bigger than the missing mantissa bits, the loss is unaffected.

**Analogy.** It's like measuring everything with a ruler that has fewer
tick marks but covers the same range. For most decisions the model is
making, "is this number ≈ 0.347 or ≈ 0.348" doesn't matter; "is this
number 0.3 or 30,000" does, and bf16 still distinguishes those clearly.

**When it fails.**
- **fp16 (not bf16) on big models.** fp16's exponent range is only 5 bits,
  so attention logits and softmax inputs frequently overflow. People worked
  around this with "loss scaling" hacks for years; bf16 retired the issue
  for most workloads.
- **Optimizer state in bf16.** If you also store Adam's moment estimates
  in bf16, tiny gradients get rounded to zero and training stalls. *Keep
  optimizer states in fp32.*
- **Reductions over many tokens.** Summing a long sequence of bf16
  values can lose precision enough to matter (e.g., loss aggregation over
  the full vocab). PyTorch's autocast already handles the common cases by
  casting reductions back to fp32; if you write a custom kernel, mind
  this.

**What we saw.** bf16 alone (added on top of TF32 + SDPA + compile) lifted
throughput from 179K → 220K tok/s with val-loss drift ≤ +0.025 nats over a
200-step probe — i.e., free.

### 1.2 SDPA / FlashAttention-2

**What.** Replace the hand-written
`softmax(QKᵀ / √d_head) · V` einsum with PyTorch's fused kernel
`F.scaled_dot_product_attention(Q, K, V, is_causal=True)`. On A100/H100
this dispatches to FlashAttention-2 under the hood.

**How.** The naive attention implementation builds the full `T × T`
attention matrix, applies the causal mask, takes softmax, and multiplies
by `V`. FlashAttention does the same math, but tiles the computation so
the `T × T` matrix is **never materialized in HBM (the GPU's main
memory)** — only small tiles live in SRAM. The trick is a clever online
softmax algorithm that lets you compute softmax block-by-block without
needing the full row at once.

**Why.** Two reasons.
1. **Memory.** Attention's `O(T²)` memory cost is what makes long contexts
   expensive. FlashAttention drops it to `O(T)` (in HBM). At `T=1024`,
   for our 16-head model this is the difference between fitting bs=24
   and OOMing at bs=4.
2. **Speed.** Tiling keeps the working set in SRAM (which is ~20× faster
   than HBM), so the whole kernel is bandwidth-bound on SRAM rather than
   HBM. Roughly 2× throughput on Ampere/Hopper.

**Analogy.** Imagine reading a book by photocopying every page first vs.
reading one page at a time. Both finish the same book; one needs a giant
table of photocopies, the other needs a single page on your desk.

**When it fails.**
- **Custom attention masks** that aren't "causal", "full", or "sliding
  window" sometimes fall back to the slow path because FA2 doesn't have
  a kernel for them. Check what backend SDPA actually picked
  (`torch.backends.cuda.sdp_kernel(...)`).
- **Very small `T`** (≤ 64). The fused kernel has overhead from launch +
  tiling; below some threshold the einsum is faster.
- **Numerical sensitivity.** FA2's online-softmax accumulator differs
  from naive softmax in the last few bits. For training this is fine; for
  hyper-precise inference comparisons it sometimes shows up.

**What we saw.** SDPA lifted throughput from 140K → 161K tok/s on the
4-layer baseline. The bigger payoff was Phase 4d, where it let us afford
ctx=1024 with bs=24 — the ctx-bump alone was −0.059 nats.

### 1.3 `torch.compile`

**What.** Capture the model's forward graph once, fuse pointwise ops,
generate optimized CUDA kernels, and reuse them on every subsequent step.

**How.** `torch.compile(model, mode="default")` runs the model once with
TorchDynamo, traces an FX graph of the operations, hands it to the
inductor backend, which produces fused Triton/CUDA kernels for entire
subgraphs (e.g., "RMSNorm → linear → SiLU → linear" becomes one kernel).
Subsequent steps skip Python overhead almost entirely.

**Why.** A typical training step has hundreds of small ops; each Python
callback and kernel launch costs a few microseconds. At our scale that's
~10–30% of the wallclock. Compile collapses many small kernels into
fewer big ones (kernel fusion) and removes the Python-side per-step
overhead.

**Analogy.** Think of it like JITting a hot loop. The first iteration is
slow because you're compiling; every iteration after is much faster.

**When it fails.**
- **Recompilation thrash.** If the input shapes change (e.g., variable
  batch size, ragged sequences, or different `cache_position` for
  inference), compile re-traces, which is expensive. We pin the batch and
  context length and drop incomplete batches.
- **`mode="reduce-overhead"`.** Uses CUDAGraphs for even lower per-step
  overhead, but **double-buffers** all activations. At bs=96 with a
  32k-vocab logit tensor, this blew our memory headroom in Phase 1.5.
  We switched to `mode="default"`, which is enough.
- **Cold inductor cache.** First-launch compile takes 30–120s. Phase 5
  hit a real failure here: a stale `/tmp/torchinductor_*` cache from a
  prior run had been GC'd, and our first launch was running at 25–40K
  tok/s instead of 105K because compile hadn't finished settling. A
  warm-up sanity probe fixed it.
- **Unsupported ops.** Custom CUDA extensions or anything that breaks
  the FX graph forces a "graph break" which limits optimization.

**What we saw.** compile lifted throughput from 161K → 180K tok/s on the
4-layer baseline (≈ +12%). The cold-cache bug also gave us a useful
operational lesson: always run one warm-up training step before assuming
you've hit steady state.

### 1.4 TF32 + cuDNN benchmark

**What.** Two unrelated single-line settings:
`torch.set_float32_matmul_precision("high")` (enables TF32) and
`torch.backends.cudnn.benchmark = True` (autotunes cuDNN kernels).

**How.**
- **TF32** is a 19-bit float format Ampere/Hopper use *internally* for
  fp32 matmul: 8-bit exponent (same as fp32), 10-bit mantissa (vs 23 for
  fp32). The user-visible types are still fp32; only the matmul accumulator
  drops a few bits. Result: ~8× faster fp32 matmul with negligible quality
  impact.
- **cuDNN benchmark** runs each unique input shape through several
  candidate kernels on the first call and picks the fastest one for
  subsequent calls.

**Why.** Both are "free" wins as long as your shapes are stable. TF32 is
why our fp32 baseline was already 140K tok/s before bf16 — most of A100's
matmul advantage is captured by TF32 alone.

**When it fails.**
- **Variable input shapes.** cuDNN benchmark explores kernels every time
  it sees a new shape, which can cause launch hiccups during the first
  few iterations of a varying-shape workload.
- **Numerical-precision-sensitive workloads.** Some scientific computing
  needs full fp32 mantissa precision; for ML training the missing 13 bits
  are well below gradient noise and don't show up in the loss.

## Group 2 — Quality wins (small per-mod, super-linear when stacked)

These are well-validated published modifications. Each one alone is a
modest improvement (about −0.003 to −0.037 nats on our 1500-step probe);
**stacked, they amplified to −0.082 nats — bigger than the sum of singles
(−0.065)**. That super-linearity is the main reason we apply all of them
together rather than picking just the strongest one.

### 2.1 QK-Norm (Query-Key Normalization)

**What.** Normalize the Query and Key vectors *per head, after RoPE,
before the dot product*. We use RMSNorm with a learnable per-head gain.

**How.** Inside each attention head, after RoPE rotates Q and K, divide
each vector by its own root-mean-square magnitude:

```
Q_norm = γ_q · Q / sqrt(mean(Q²) + ε)
K_norm = γ_k · K / sqrt(mean(K²) + ε)
attention_logits = Q_norm · K_normᵀ / √d_head
```

**Why.** Without normalization, individual entries of `Q · Kᵀ` can grow
without bound during training. Once one logit is much bigger than the
rest, softmax sharpens onto a single key, and the gradient through that
single sharp peak gets enormous. One unlucky step and the head diverges.

QK-Norm guarantees Q and K are unit-RMS, so the dot products live in a
predictable range. The model can still learn sharp attention patterns
(via the per-head learnable gain γ), but it can't *accidentally* drive a
logit to ∞ via a runaway gradient.

**Analogy.** It's like requiring every meeting attendee to speak at
similar volume. Anyone can still make a strong point, but nobody can
shout everyone else into silence with one bad outburst.

**Why it's especially helpful here.** It lets you train at higher LR
without divergence — which matters because Muon (next section) wants
*much* higher LR than AdamW. QK-Norm is cheap insurance that the higher
LR doesn't blow up the attention layers.

**When it fails.**
- **Already-stable architectures at low LR.** If your model never had
  attention divergence, QK-Norm adds parameters and a tiny compute cost
  without measurable benefit. The win is biggest at large LR / large
  scale.
- **Without learnable gain.** A pure unit-RMS constraint can be
  *too* restrictive. The learnable γ is what lets the model still
  produce sharp attention when needed; remove it and you cap the model's
  representational power.

**What we saw.** Phase 1 single-mod: −0.013 nats at 1500 steps. Modest in
isolation but the stack effect was much larger.

### 2.2 Weight tying + reduced embedding init

**What.** Two coupled changes:
1. **Tying:** make the LM head and token embedding matrices the *same*
   tensor — `lm_head.weight = token_embeddings.weight`.
2. **Smaller init:** initialize the embedding from `N(0, 1/d_model)` instead
   of `N(0, 1)`.

**How.** Both matrices are `(vocab_size, d_model)`. The token embedding
maps `token_id → vector`; the LM head maps `vector → logits` (one logit
per token). They're conceptually inverses of each other; tying says "use
the same lookup table for both directions."

The smaller init handles a numerical gotcha. With `N(0, 1)` embeddings
and a tied LM head, the initial logits have variance proportional to
`d_model` — for d=1024 that's `√1024 ≈ 32`. The softmax over 32 ± 32 logits
is wildly peaked from step zero and the model spends the first several
hundred steps just *unlearning* its randomly-confident initial state.
Using `1/√d_model` for the embedding makes the initial logits unit
variance, so the softmax is roughly uniform at init — which is what you
want.

**Why.**
- **Tying.** The vocab-side mapping is fundamentally one map, so why
  learn it twice? Saves ~16M parameters at vocab=32k / d=512, ~33M at
  d=1024. That memory pays for either a deeper model or a longer
  context. Also tends to improve generalization a bit because the
  embeddings get gradient signal from both directions.
- **Smaller init.** Without this, tied embeddings are *worse* than
  untied — you lose 0.04+ nats just because the initial loss landscape
  is bad. With it, tied + small-init beats untied at the same compute.

**Analogy.** Tying is "use one English-word dictionary for reading and
writing, instead of two." Smaller init is "make sure you don't start the
day already shouting."

**When it fails.**
- **Tying without smaller init.** This was Phase 1's main negative
  result: tied embeddings *with* `N(0,1)` init regressed by +0.041 nats
  vs untied. The combination is what works; either ingredient alone is
  worse.
- **Encoder-decoder models.** When source and target vocabularies are
  different (translation), you can only tie within one side, and even
  then the trade-off varies.
- **Very small vocabularies.** The parameter savings are proportional to
  vocab size; for a 1k-vocab byte-level model the savings are
  negligible.

**What we saw.** Tied embeddings + std=1/√d together: −0.020 nats and
~33M fewer parameters.

### 2.3 Logit soft-cap

**What.** Apply `cap · tanh(logits / cap)` with `cap = 30` to the
final logits before softmax.

**How.** `tanh(x)` is `~x` for `|x| ≪ 1` and saturates to `±1` for
`|x| ≫ 1`. The wrapped form `cap · tanh(x / cap)` is `~x` for
`|x| ≪ cap` and saturates to `±cap` for `|x| ≫ cap`. So logits below
±30 pass through nearly unchanged; logits above ±30 get smoothly
squashed.

**Why.** With bf16 + a 32k-vocab head, an occasional rare-token logit can
spike to ±50 or ±100 (e.g., on a "this token *cannot* appear here"
prediction). bf16's reduced precision loses information in such large
softmax inputs, and the gradient through that giant logit is a mess. The
soft-cap keeps logits in a numerically clean range without changing the
loss landscape for the 99.9% of logits that are normally sized.

The "soft" matters: `tanh` is differentiable everywhere, unlike a hard
clip. So gradient flow stays clean.

**Analogy.** It's a gradual speed limit, not a brick wall. You can drive
fast in normal conditions; if you try to drive infinity-fast, the
mechanism gently pushes you back.

**When it fails.**
- **`cap` set too low.** `cap = 5` would distort the loss landscape for
  *most* logits and hurt the model. `cap = 30` is large enough that
  normal logits pass through unchanged but small enough to catch
  outliers. (Gemma-2 uses 30 for the same reason.)
- **Already-stable training.** If you're at fp32 + low LR + small vocab,
  soft-cap adds a tanh per token for no real benefit.

**What we saw.** Single-mod: −0.014 nats. Combined with z-loss it
catches a different failure mode (outliers vs collective scale drift),
which is why both help despite seeming similar.

### 2.4 Z-loss

**What.** An auxiliary loss term added to cross-entropy:

```
total_loss = cross_entropy + z_weight · mean(logsumexp(logits)²)
```

with `z_weight = 1e-4`.

**How.** Recall that
`cross_entropy = logsumexp(logits) − logits[target]`. The
`logsumexp(logits)` is the log of the partition function — it's an
*absolute* scale that cross-entropy itself is invisible to (CE only
cares about the gap between the target logit and the rest). The z-loss
explicitly penalizes `logsumexp(logits)` from drifting away from 0.

**Why.** Cross-entropy *only* constrains relative logits. The model can
shift all logits up by 100 simultaneously and CE doesn't change. But
under bf16, a logsumexp of 100 has way fewer usable bits than a logsumexp
of 0. Over a long training run the absolute scale of logits can drift,
slowly making the softmax less accurate. The z-loss term is a tiny anchor
that says "keep logsumexp ≈ 0, please."

It's *synergistic* with the soft-cap:
- Soft-cap bounds **individual outlier** logits.
- z-loss bounds the **collective scale** of all logits at once.
You need both because they handle different failure modes.

**Analogy.** Soft-cap is "no one student can shout"; z-loss is "the whole
class shouldn't drift toward shouting on average."

**When it fails.**
- **Weight too high.** `z_weight = 1e-2` would dominate cross-entropy and
  hurt actual prediction quality. The PaLM paper uses 1e-4; we use 1e-4.
- **fp32 training without precision concerns.** The absolute scale of
  logsumexp matters way less when you have 23 mantissa bits. z-loss is
  most valuable in bf16 + long training.

**What we saw.** Single-mod: −0.003 nats. Smallest individual win, but
removing it made the bf16 logsumexp drift visible in long-run logs.

## Group 3 — Speedrun-style mods (the lottery tickets)

These come from recent NanoGPT-speedrun-style work. They're recent enough
that they haven't been validated across as many scales as Group 2 mods.
Some generalize, some don't. **Always ablate before committing.** Out of
five mods we tried, three were kept and two were dropped.

### 3.1 Muon optimizer (KEPT — biggest single win at −0.192 nats)

**What.** A new optimizer that replaces AdamW for the **2D weight
matrices inside transformer blocks** (Q/K/V/O projections, FFN W1/W2).
AdamW continues to handle 1D parameters (norm gains, biases) and the
embedding table.

**How.** For each parameter `W` Muon manages:

1. Compute the gradient `g`.
2. Update a momentum buffer: `m = β · m + g` with `β = 0.95`.
3. **Orthogonalize** `m` via 5 Newton-Schulz iterations to get `O ≈ U Vᵀ`,
   where `m = U Σ Vᵀ` is the SVD of `m`. This effectively divides every
   singular value by itself — leaving a matrix with all singular values
   equal to 1 (i.e., orthogonal-ish).
4. Apply the update: `W = W − lr · O` with `lr = 0.02`.

The Newton-Schulz iteration is the trick that makes this practical: it
approximates `m / sqrt(mᵀm)` (matrix inverse-square-root) using only
matrix multiplies — no SVD needed. Each iteration is a fixed polynomial
in `m` and runs ~13% per-step overhead on our shapes.

**Why orthogonalization helps.** Imagine the gradient `g` has a big SVD —
say one singular direction has σ₁ = 100, the next σ₂ = 1, the rest near
zero. AdamW (because of its element-wise second-moment normalization)
will partially correct for this, but its update is still dominated by σ₁.
The model takes one big step in the σ₁ direction and tiny steps in the
others — essentially using only one direction per step.

Muon's orthogonalized update has σ₁ = σ₂ = ... = 1: every singular
direction gets the *same* magnitude of update. The model takes
informative steps in *all* directions of the gradient subspace at once.
Empirically this is ~2× more sample-efficient on 2D matmul weights.

**Why it's restricted to the matmul matrices.** Newton-Schulz needs a 2D
matrix to orthogonalize. For 1D parameters (norm gains, biases) it's
undefined; for the embedding/lm_head, the orthogonalization rescale
doesn't make physical sense (you'd be renormalizing the *vocabulary*
direction, which destroys the meaning of word distance). So:
- 2D internal weights → Muon
- 1D weights and the (V × d) embedding/lm_head → AdamW

**Analogy.** AdamW is doing 100 push-ups with the same dominant arm.
Muon spreads the workload across all directions equally — it's more like
a balanced full-body routine. Same total work, more useful per rep.

**Hyperparameters.**
- `muon_lr = 0.02` (NanoGPT default)
- `momentum = 0.95`
- `ns_steps = 5` (more iterations = closer to true orthogonalization,
  fast diminishing returns past 5)

The Muon LR is ~10–50× higher than the AdamW LR because Muon's update
is already an orthogonalized direction — the LR just controls step size,
not direction-magnitude.

**When it fails.**
- **Without QK-Norm or other stability mods.** The high effective step
  size makes attention more prone to divergence. We always use Muon
  with QK-Norm.
- **Tiny matrices (d_model < 64 or so).** Newton-Schulz overhead
  dominates and the orthogonalization is over-constraining for low-rank
  matrices.
- **Vocab/embedding matrices.** Orthogonalizing across the vocab
  direction would mix unrelated tokens together; same for the LM head.
  *Always* use AdamW for these.
- **Without gradient clipping.** Newton-Schulz on a matrix with huge
  singular values doesn't converge in 5 steps. Standard global gradient
  clipping (1.0) before the optimizer step is enough.

**What we saw.** Phase 3: AdamW val@2000 = 4.3056 → Muon-mixed val@2000
= 4.1160, **−0.190 nats** for ~13% throughput cost. The single biggest
win in the entire 7.5 plan.

### 3.2 WSD schedule (Warmup-Stable-Decay) (KEPT — −0.207 nats from decay phase alone)

**What.** A learning-rate schedule with three explicit phases:
1. **Warmup** (first 100 steps): LR ramps linearly from 0 to peak.
2. **Stable** (next 80% of training): LR stays at peak, flat.
3. **Decay** (last 20% of training): LR ramps linearly from peak to 0.

**How.** Just a piecewise-linear function of step number. No moving parts
or hyperparameters beyond `decay_frac = 0.2` (the fraction of total
steps spent in decay) and `warmup_steps = 100`.

**Why.**
- **Warmup.** Adam/Muon's momentum estimates are biased toward zero at
  step 0 — the first few gradient samples disproportionately set the
  moment estimates. If you run full LR from step 0, those first noisy
  samples dominate everything and the model can overshoot into a bad
  region of parameter space. Warmup gives the moment estimates a chance
  to fill in before LR is full-strength.
- **Stable phase.** With high LR the parameters are bouncing around in a
  basin — the bouncing radius is roughly proportional to LR. Within that
  basin, the model is exploring; it's *not* stuck.
- **Decay phase (the magic).** As LR shrinks, the bouncing radius
  shrinks with it. The parameters settle into a sharper local minimum
  *within the same basin*. This is the same mechanism that made cosine
  beat fixed-LR in Section 7.2 — but WSD makes it explicit and easy to
  control: the decay window is exactly the last `decay_frac` of training.

**Why it beats cosine at fixed compute.** Cosine spends most of its time
already partly-decayed (the curve is convex). WSD spends 80% of training
at full LR exploring, then dumps all the LR-shrinkage into the last 20%.
Empirically this finds slightly better minima at the same compute.

**Analogy.** Imagine searching a city for the lowest point on a map.
- *Stable phase:* drive around fast — you cover lots of ground but can't
  tell hills from ditches because you're going too fast.
- *Decay phase:* park, then walk slowly downhill from where you stopped.
  You can feel small slope changes and find the true bottom of the basin.

**When it fails.**
- **Decay fraction too small.** With `decay_frac = 0.05` the late LR
  barely shrinks and you don't get the snapshot benefit.
- **Decay fraction too large.** With `decay_frac = 0.5` you spend half
  your compute at low LR not exploring; the stable phase's basin search
  is cut short.
- **Decay starts before exploration is done.** Common at small step
  budgets. *Our Phase 4a saw this directly:* WSD over 2,000 steps
  contributed −0.121 nats; WSD over 45,000 steps contributed −0.207
  nats. The decay needs *room* to do its job — the basin you settle into
  has to be a good one, which requires having explored long enough to
  find one.

**What we saw.** WSD (warmup=100, decay_frac=0.2) was the kept choice.
The 36,000 → 45,000 step decay phase alone in the final run dropped val
loss from 3.3975 to 3.1904 — bigger than the entire Tier-1 mod stack
(−0.082 nats).

### 3.3 Longer context with smaller batch (KEPT — −0.059 nats)

**What.** Train at `ctx=1024, bs=24` instead of `ctx=256, bs=96`. Tokens
per step are unchanged (24,576 either way) — same throughput, longer
sequences.

**How.** Just change the data loader to slice 1024-token windows
instead of 256. Attention's `O(T²)` cost was the historical reason small
context was preferred; FlashAttention-2's `O(T)` memory removes that
constraint at 1024.

**Why.** A model trained on 256-token windows can only learn dependencies
up to 256 tokens. At 1024 it can learn paragraph-level relationships:
an earlier sentence's named entity, a topic phrase from two paragraphs
ago, a conditional clause referenced later. The autoregressive loss
*automatically* exploits these dependencies if the model has the
context window to see them.

**Tokens per step are unchanged**, so the model sees the same total
amount of training data. The win is purely the *quality* of the gradient
signal: gradients computed on longer contexts contain more information
about long-range structure.

**Analogy.** It's the difference between learning to write by reading
sentence fragments vs reading whole paragraphs. Same number of words
per day, but the structural patterns you can learn are very different.

**When it fails.**
- **No long-range dependencies in the data.** TinyStories is mostly
  single-paragraph kid stories — going from ctx=256 to ctx=1024 helps
  much less. OpenWebText is full of multi-paragraph articles, so the win
  is real.
- **Memory pressure.** Without SDPA's `O(T)` memory, ctx=1024 simply
  doesn't fit at our model size. Pairs naturally with FA2.
- **Smaller batch noise.** Batch size 24 has slightly noisier
  gradient estimates than 96. We didn't see this hurt at our scale, but
  at smaller `d_model` it could matter.

**What we saw.** Phase 4d: val@2000 went from 3.9951 (ctx=256, bs=96) to
3.9365 (ctx=1024, bs=24), **−0.059 nats** at the same tokens/step.

### 3.4 ReLU² FFN (DROPPED — +0.020 nats regression)

**What.** Replace the SwiGLU FFN
(`W2(SiLU(W1·x) ⊙ V·x)`) with a simpler squared-ReLU FFN
(`W2(ReLU(W1·x)²)`). Two matmuls instead of three; no gating.

**How.** The activation is `f(x) = max(x, 0)²`. It's piecewise: zero for
negative inputs, `x²` for positive. The gating matrix `V` is removed
entirely, saving one matmul per layer.

**Why proposed.** Faster (one fewer matmul → ~13% throughput win) and
the speedrun's small-scale experiments suggested the quality is
comparable to SwiGLU. ReLU² has a steeper-than-linear positive branch,
which is hypothesized to give the network slightly different
representational properties than SwiGLU.

**Why it failed for us.** It generalized worse to our setting (d=1024,
L=8, OWT, 32k vocab, 2000 steps). The speedrun's evidence was at much
smaller scales (d=256, GPT-2 small benchmark). Faster *and worse* is
strictly worse inside a fixed compute envelope: every saved second per
step is more than canceled by the worse loss per step.

**When it fails (general lesson).** This is the canonical "speedrun mod
that doesn't transfer" — speedrun-style experiments target minimum
wallclock at fixed model size; they don't necessarily extrapolate to
different scales, datasets, or training durations. The assignment
specifically warned about this and we hit it.

**What we saw.** Phase 4b: val@2000 went 3.9951 → 4.0149 (+0.020 nats).
Dropped, kept SwiGLU.

### 3.5 Value-embedding skip / U-net skip (DROPPED — within ±0.005 noise)

**What.** Re-add the input token-embedding matrix to the residual stream
at a deeper layer (e.g., layer L/2 = 4). Conceptually like a U-net skip
connection from the input to the middle of the network.

**How.** At layer 4, instead of `h = h + attn(h) + ffn(h)`, do
`h = h + attn(h) + ffn(h) + token_embed[input_ids]`. The input
embeddings get a fresh shortcut to the deeper layers.

**Why proposed.** Helps the LM head recover surface-level features (the
identity of nearby tokens) that earlier attention layers may have smeared
into more abstract representations. NanoGPT speedrun reports this as a
small but real win.

**Why it didn't help for us.** Within ±0.005 nats of the no-skip
baseline at our shape — basically noise. Possible reasons:
- Our model is shallower (L=8) than the speedrun's typical L=12, so the
  surface features aren't being smeared as much by deep layers.
- Our 2,000-step probe might not be long enough for the skip to
  differentiate.
- It might be redundant with weight tying, which already gives the LM
  head direct access to the embedding table.

We pre-staged the flag in the codebase in case it generalizes at other
shapes — but didn't include it in the final config because there was no
positive evidence at the scale we trained at.

**When it fails (general lesson).** Mods that reach the *same place* by
*different paths* are often redundant. Weight tying already routes
embedding info to the LM head; an extra skip from input to mid-stack is
solving an adjacent problem that's already partly solved. The lesson:
when stacking mods, watch for redundancy with what's already there.

## Group 4 — Methodology (how we ran the search)

These aren't training-time modifications; they're decisions about *how*
to run experiments efficiently. They cut the cost of finding a good
config from "exhaustive grid search" to "a handful of cheap probes".

### 4.1 LR re-anchoring

**What.** Whenever the loss landscape changes meaningfully (new
hardware, new infra, new model size, new optimizer, new mods stack),
re-tune the learning rate before continuing.

**How.** A 3-LR sweep at `{lr_old / √2, lr_old, lr_old · √2}` for ~1500
steps each. Pick the winner; that becomes the new anchor for downstream
phases.

**Why.** Optimal LR is a function of the entire optimization landscape:
batch size, model dimension, optimizer, schedule, and even precision can
shift it. If you change three things at once and don't re-tune, you may
be evaluating each new change at a *bad* LR, making it look worse than
it is.

We re-anchored at four points:
- Phase 0.5: new infra (bf16 + SDPA + compile)
- Phase 1.5: new arch (QK-Norm enabled)
- Phase 2c: new model size (d=1024, L=8)
- Phase 4.5: new mods stack (WSD + ctx=1024)

Each sweep costs ~30 min; the final run costs ~3 hours. Re-anchoring is
cheap insurance against committing to the wrong LR.

**When it fails.** When you're tuning *too aggressively*. If you re-anchor
every single phase, you're spending more on tuning than on the actual
experiment, and noise in the LR sweeps can lead you astray.

**What we saw.** Phase 4.5: lr=1.0e-3 (the previous anchor) lost to
lr=1.414e-3 by −0.016 nats at val@2000. Cheap to find, would have cost
us −0.016 nats × 22.5 (the 45k/2k ratio) ≈ −0.36 nats over the full run
if we hadn't checked.

### 4.2 Cumulative greedy ablation

**What.** Try Tier-2 mods one at a time on top of the previous best.
Keep what helps, drop what doesn't, then try the next mod on top of the
new best.

**How.**
```
best = baseline
for mod in tier_2_mods:
    candidate = best + mod
    if val(candidate) < val(best):
        best = candidate
```

**Why greedy + cumulative.** Mods can interact super-linearly. The
Tier-1 single-mod probes had a sum-of-singles of −0.065 nats; stacked,
they hit −0.082 nats. The only way to see super-linear interactions is
to stack mods cumulatively. Single-mod-from-baseline ablations would
have under-counted the benefit of every Tier-1 mod.

**Why not exhaustive.** A full ablation matrix over `n` mods is
`O(2ⁿ)`. With our 5 Tier-2 mods that's 32 configs × 30 min each = 16
hours of probing. Greedy gets us 90% of the answer in `O(n)` runs.

**When it fails.**
- **Negative interactions.** If two mods individually help but
  *together* hurt, greedy will pick whichever you tried first and miss
  the other. Mitigation: order mods by expected magnitude — try the big
  ones first.
- **Order dependence.** Greedy can find different "best" configs
  depending on order. We don't fully solve this; we use it as a fast
  heuristic and trust the final-run number to validate.

**What we saw.** Greedy ablation kept WSD + ctx=1024, dropped ReLU² + U-net
skip. The kept-pair had cumulative −0.180 nats vs the Phase-3 baseline
at 2000 steps. Total Phase-4 ablation cost: ~30 min for 4 runs.

### 4.3 μP-inspired LR scaling guess

**What.** When scaling model dimension from `d_old` to `d_new`, divide
the LR by `√(d_new / d_old)` as a *starting guess* for the LR sweep at
the new size.

**How.** From the maximal-update-parameterization (μP) framework: if you
parameterize correctly, the optimal LR scales as `1/√d_model`. Apply this
as a starting point for the next LR sweep.

**Why.** μP is a theoretical framework that predicts which LR carries
over across scales. Even when the assumptions don't perfectly hold
(short training, fixed-LR schedule, etc.), the rule is a good *guess* —
much better than starting from `lr=2e-3` regardless of model size.

**When it fails.** It's an asymptotic prediction. At fixed LR / 2,000
steps it's only roughly right. We seeded Phase 2c at `2e-3 / √2 ≈ 1.41e-3`
(μP guess); the actual winner was `1.0e-3` (lower than the guess). The
mini-sweep around the guess catches the discrepancy.

**Lesson.** Use theory to seed the search, then verify with a small
sweep. Don't trust theory as a substitute for empirical checking.

### 4.4 Wallclock-budgeted training

**What.** A `--max-wallclock-sec` flag in the training script. If total
elapsed time exceeds the cap, the loop runs one final val + checkpoint
and exits cleanly.

**How.** A simple `if time.time() - start > cap: break` after each step,
plus a forced final-val + final-checkpoint pass before the break so
the budget-terminated run produces useful artifacts.

**Why.** Throughput can drift during a multi-hour run (compile cache
issues, thermal throttling, other tenants on shared infra, etc.). A
fixed `--max-steps` doesn't adjust if throughput is lower than expected.
A wallclock cap is a belt-and-braces guard against overrunning the
compute envelope.

**When it doesn't fire.** Most of the time, ideally — it's insurance.
Our final run finished naturally at 10,584 s of an 11,400 s cap, so
the guard never triggered. But the *threat* of it triggering shapes
how you design the schedule (we tuned `max_steps=45000` so WSD's decay
ends just before the wallclock cap).

**Lesson.** When training in a fixed compute envelope, *always* have a
wallclock guard. Step counts are estimates; wallclock is what the budget
actually charges you in.

## Putting it all together — the rough decision tree

If you're approaching a similar leaderboard from scratch, here's the
mental model that worked for us:

1. **Start with infrastructure.** bf16, SDPA, compile, TF32 — turn them
   all on by default. Verify identical loss and faster wallclock.
2. **Stack the Tier-1 quality wins.** QK-Norm, weight-tying-with-small-init,
   logit soft-cap, z-loss. They're well-validated and individually
   small but compound super-linearly.
3. **Re-anchor LR after every meaningful change.** Cheap probes save
   expensive final-run regrets.
4. **For Tier-2 (speedrun) mods, ablate cumulatively.** Some will win,
   some will lose. The biggest wins (Muon, WSD) are worth the per-mod
   probing cost.
5. **Tune step count to your wallclock, not the other way around.** The
   schedule's decay window has to land *inside* your compute envelope.
6. **Always have a wallclock guard** as belt-and-braces.

| Step | Decision | Cost | Risk if skipped |
|---|---|---|---|
| Infra | bf16+SDPA+compile+TF32 | ~30 min probe | 7× slower training |
| Tier-1 stack | QK-Norm, tied embed+small init, soft-cap, z-loss | ~14 min ablation | Miss −0.082 nats super-linear stacking |
| LR re-anchor | 3-LR sweep after each change | ~30 min × 4 | Wrong LR throughout |
| Muon | Replace AdamW for 2D internal weights | ~25 min ablation | Miss −0.192 nats (single biggest win) |
| WSD | Replace cosine schedule | (rolled into Phase 4) | Miss −0.207 nats decay-phase win |
| Longer ctx | ctx=256 → 1024 with bs adjustment | ~15 min | Miss −0.059 nats |
| Speedrun mods | ReLU², U-net skip — *always ablate* | ~15 min | Risk +0.020 nats regression |
| Wallclock guard | `--max-wallclock-sec` | ~free | Risk overrunning the budget |
